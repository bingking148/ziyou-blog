如果你想学大模型应用，最不该做的就是把这些名词当成零散知识点背下来。真正重要的是看清它们之间的关系：AI 是最大的技术领域，LLM 是其中负责理解与生成语言的模型，Agent 是让 LLM 能调用工具、完成任务的应用形态；提示词是人类控制模型意图的接口，HTTP 和 JSON 是把请求送到模型的通道，而“无状态”决定了大模型看起来会“失忆”。这篇文章就把这张概念网络讲清楚。

## 1. AI、LLM、Agent：三个越缩越小的圈

可以把三者看成三层：

- **AI（人工智能）**：最大的圈，泛指让机器模拟人类智能的技术总称。
- **LLM（Large Language Model，大语言模型）**：AI 里的一个分支，用海量文本训练出来的语言模型。它的核心能力是根据上文预测下一个词，所以能续写、回答、总结、翻译、改写。
- **Agent（智能体）**：给 LLM 装上手脚后的产物，不只回答问题，还能查资料、调用工具、执行多步任务。

用一个比喻说：LLM 是大脑，Agent 是把大脑装进了一个会做事的机器人身上。大脑负责理解和推理，机器人还要有眼睛、手、记忆和行动流程。

## 2. Agent 的五个零件：LLM、Tool、RAG、Skill、Memory

一个常被引用的公式是：

> **Agent = LLM + Tool + RAG + Skill + Memory**

这句话背后的分工很清楚：

| 零件 | 作用 | 类比 |
|---|---|---|
| **LLM** | 理解用户输入，推理下一步该做什么 | 大脑 |
| **Tool** | 调用搜索、计算器、代码执行器、数据库等外部能力 | 手脚 |
| **RAG** | 从私有文档或知识库中检索内容，再交给模型回答 | 外挂资料柜 |
| **Skill** | 预设好的动作流程，例如“审校文章”“生成图卡” | 岗位技能 |
| **Memory** | 保存跨轮次的上下文，让 Agent 记住之前聊过什么 | 工作备忘录 |

其中 RAG 特别值得单独理解。它不是让模型凭空“记住”你的资料，而是在用户提问后，先从你的文档里检索相关片段，再把这些片段放进提示词里让模型参考。所以 RAG 更像“先查资料，再回答”，而不是“把所有资料永久塞进模型脑子里”。

## 3. 大模型发展时间线：为什么 Transformer 是地基

大模型不是突然出现的，有几条关键线索：

- **2017 年**：Google 提出 Transformer 架构。它解决了序列建模中的关键问题，让模型能更好地关注上下文中的重点信息，是后来多数大模型的基础。
- **2018 年**：OpenAI 发布 GPT 1.0，Google 发布 BERT。前者偏向生成式语言建模，后者偏向理解类任务，两条预训练语言模型路线同年开局。
- **2022 年**：OpenAI 上线 ChatGPT。大模型从论文和实验室产品，变成普通人浏览器里可以直接使用的东西。
- **2025 年**：DeepSeek 免费开源，进一步推动“开源模型人人可部署”的路线，让本地部署和使用大模型的门槛降低。

理解这条时间线的意义在于：大模型应用的爆发不只是“模型变聪明”，还包含架构、产品形态和开源生态的连续变化。

## 4. 主流模型版图：国外和国内代表

学习大模型应用时，最好把模型分成两类视角：一类是云端模型，另一类是本地模型。云端模型通常能力更强、部署简单，但需要联网和 API Key；本地模型隐私性更好、可以离线运行，但受设备资源限制。

| 阵营 | 代表模型 | 出品方 |
|---|---|---|
| 国外 | Gemini | Google |
| 国外 | GPT | OpenAI |
| 国外 | Claude | Anthropic |
| 国内 | DeepSeek、Kimi、GLM、通义千问、豆包 | DeepSeek / 月之暗面 / 智谱 / 阿里 / 字节 |
| 国内 | 盘古 | 华为 |

这些模型背后的接口形态不一定完全相同，但很多服务和工具都在向 OpenAI Chat Completions 的格式靠拢，所以学习时重点不是死记某个模型名字，而是理解“模型服务如何被调用”。

## 5. 提示词：人类控制 LLM 的接口

提示词（Prompt）是你发给模型的指令。它可以是一个问题、一段任务描述，也可以是一整套角色、任务、要求和输出格式。提示词工程（Prompt Engineering）就是通过设计和迭代提示词，让模型输出更接近预期。

一个最小可用的提示词模板是：

```text
【角色】你是一位有 10 年经验的雅思写作考官
【任务】批改下面这篇作文并打分
【要求】
1. 按官方 4 项评分标准逐项打分（各 0-9 分）
2. 指出 3 个主要问题并给出修改建议
3. 提供一段改进后的范文（150 词）
【输入】{作文内容}
```

这个模板可以继续扩展成六个检查项：

1. **角色**：告诉模型以什么身份回答。
2. **任务**：明确要它做什么。
3. **步骤**：复杂任务要拆解，避免漏答。
4. **示例**：给模型对齐输入输出样式。
5. **格式**：要求表格、列表、JSON 或固定段落。
6. **语气**：控制正式、口语、简洁、幽默等风格。

提示词不是玄学，而是一次和模型对齐需求的过程。输出不好时，先检查你的任务是否说清楚，而不是急着换模型。

## 6. 网络基础：模型 API 请求是怎么走的

调用大模型 API 时，背后通常有几层东西在工作。

### IP、域名、端口

- **IP 地址**用来定位设备。IPv4 常见写法是四段数字，例如 `132.12.86.125`。
- **域名**方便人记忆，例如 `www.baidu.com`。DNS 负责把域名解析成 IP。
- **端口**用来定位设备上的程序。HTTP 默认端口是 80，HTTPS 默认端口是 443。
- `127.0.0.1` 是本机回环地址，`localhost` 也是本机。后面连本地模型服务时会经常看到它。

### HTTP 的三个关键特点

HTTP 是客户端和服务器之间传输数据的规则。它有三个特点：

- **基于文本**：请求和响应内容是文本格式，便于阅读和调试。
- **请求-响应模型**：客户端先发请求，服务器再返回响应。
- **无状态**：服务器默认不记住之前和这个客户端发生过什么。

第三点对大模型应用尤其重要。你以为聊天工具记得上文，其实很多情况下是客户端把历史消息又发了一遍。

### 请求与响应

一个 HTTP 请求通常包含：

- 请求行：请求方法、资源路径、协议版本。
- 请求头：例如内容类型、认证信息。
- 请求体：真正发送给服务器的数据。

响应也类似：

- 响应行：协议版本和状态码。
- 响应头：服务器返回的元信息。
- 响应体：模型返回的数据。

常见状态码可以先记四个：

| 状态码 | 含义 | 排查方向 |
|---|---|---|
| 200 | 成功 | 正常 |
| 400 | 请求参数错误 | 检查请求体 |
| 404 | 资源不存在 | 检查 URL 或路径 |
| 500 | 服务器错误 | 先看服务端，再看是否触发限流或异常 |

### JSON：大模型 API 的通用数据格式

JSON 长得像 Python 字典，也是键值对结构。大模型请求里常见的 `model`、`messages`、`stream` 等字段，通常就用 JSON 表示。

一个典型请求体如下：

```json
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "Hello!"}
  ],
  "stream": false
}
```

注意 JSON 的几个细节：

- 所有 key 必须用双引号。
- 字符串也用双引号。
- 布尔值是小写的 `true` 和 `false`，不是 Python 里的 `True` 和 `False`。
- 对象用 `{}`，列表用 `[]`。

## 7. messages 三种角色：system、user、assistant

大模型 Chat API 里最重要的结构之一就是 `messages`。它是一个消息数组，每条消息都有 `role` 和 `content`。

- **system**：设定模型身份、规则、风格和限制。例如“你是一个简洁的客服助手”。
- **user**：用户真正提出的问题或指令。
- **assistant**：模型之前的回复。

```json
{
  "messages": [
    {"role": "system", "content": "你是一个简洁的助手，回答不超过三句话。"},
    {"role": "user", "content": "解释一下什么是 RAG。"}
  ]
}
```

system 不是可有可无的装饰。它相当于给模型划定工作边界，能显著影响回答风格和稳定性。

## 8. 无状态与“会话记忆滚雪球”

很多初学者会遇到这种问题：

> 第一轮：12 个苹果，3 个人怎么分？  
> 模型：每人 4 个。  
> 第二轮：那 2 个人呢？  
> 模型：你是指哪两个人？

这不是模型“忘了”，而是 HTTP 和模型服务默认无状态。第二轮请求里没有第一轮的内容，模型自然不知道“那”指的是什么。

解决方案是把历史消息一起发给模型：

```json
{
  "messages": [
    {"role": "system", "content": "你是一个简洁的助手。"},
    {"role": "user", "content": "12 个苹果，3 个人怎么均分？"},
    {"role": "assistant", "content": "每人 4 个，12 ÷ 3 = 4。"},
    {"role": "user", "content": "那 2 个人呢？"}
  ]
}
```

这样模型看到完整上下文，就能回答“每人 6 个”。但这也带来一个问题：消息越长，消耗的 token 越多。所以实际工程里需要做截断、摘要或持久化记忆管理。

## 9. 把整张概念网络串起来

一张更完整的链路是这样的：

```text
用户输入
  ↓
提示词模板：角色 + 任务 + 要求
  ↓
messages 数组：system / user / assistant
  ↓
JSON 请求体
  ↓
HTTP 请求发送到模型 API
  ↓
LLM 根据上下文预测并生成文本
  ↓
HTTP 响应返回 JSON
  ↓
程序解析响应并展示给用户
```

如果是普通对话，这个链路到“返回结果”就结束了。如果是 Agent，则会继续扩展：

```text
用户目标
  ↓
LLM 判断需要什么信息或工具
  ↓
Agent 调用搜索、数据库、代码执行器或 RAG
  ↓
把工具结果拼回上下文
  ↓
LLM 继续推理
  ↓
产出最终答案或执行动作
```

## 10. 学习时应该抓住的四个关系

学完这些概念后，可以用四个问题检验自己是否真的理解了：

1. **LLM 和 Agent 的区别是什么？**  
   LLM 是模型，负责语言理解和生成；Agent 是应用，包含模型、工具、知识库、技能和记忆。

2. **提示词和 messages 有什么关系？**  
   提示词是写给模型的任务描述；messages 是把 system、user、assistant 等内容组织起来的 API 结构。

3. **JSON 和 HTTP 各负责什么？**  
   HTTP 负责传输规则，JSON 负责组织数据内容。

4. **为什么模型会“失忆”？**  
   因为服务默认无状态。所谓记忆，通常是客户端把历史上下文重新发送给了模型。

这四个问题能答清楚，你就已经把 AI、LLM、Agent、提示词、HTTP、JSON 和上下文记忆这张概念网络连起来了。
